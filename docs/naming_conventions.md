## 📌 Ground Rules

| Rule | What it means |
|------|---------------|
| **snake_case** | Lowercase letters only, words separated by underscores (`_`). |
| **English only** | Every object name is written in English. |
| **No reserved words** | Never name an object after an SQL reserved keyword. |

```text
✅ customer_info
❌ CustomerInfo
❌ customer-info
```

## ⚡ Quick Reference

| Object | Pattern | Example |
|--------|---------|---------|
| Bronze table | `<sourcesystem>_<entity>` | `crm_customer_info` |
| Silver table | `<sourcesystem>_<entity>` | `crm_customer_info` |
| Gold table | `<category>_<entity>` | `dim_customers`, `fact_sales` |
| Surrogate key | `<table_name>_key` | `customer_key` |
| Technical column | `dwh_<column_name>` | `dwh_create_date` |
| Stored procedure | `load_<layer>` | `load_bronze` |

## 🗂️ Naming Tables by Layer

### 🥉 Bronze

Tables keep the exact name they have in the source system, with the source system as a prefix. Nothing gets renamed.

```text
<sourcesystem>_<entity>
```

| Part | Description |
|------|-------------|
| `<sourcesystem>` | Short name of where the data comes from (e.g. `crm`, `erp`). |
| `<entity>` | The original table name, untouched. |

**Example:** `crm_customer_info` holds customer information coming from the CRM.

### 🥈 Silver

Silver follows the same pattern as Bronze, so a table keeps its identity as it moves from one layer to the next.

```text
<sourcesystem>_<entity>
```

| Part | Description |
|------|-------------|
| `<sourcesystem>` | Short name of where the data comes from (e.g. `crm`, `erp`). |
| `<entity>` | The original table name, untouched. |

**Example:** `crm_customer_info` is the cleaned version of the Bronze table with the same name.

### 🥇 Gold

Gold is the business-facing layer, so names move away from the source and describe what the table means for the business. Every name starts with a category prefix.

```text
<category>_<entity>
```

| Part | Description |
|------|-------------|
| `<category>` | The role of the table in the model (see the table below). |
| `<entity>` | A descriptive, business-aligned name (e.g. `customers`, `products`, `sales`). |

**Examples:**

- `dim_customers`: dimension table with customer data.
- `fact_sales`: fact table with sales transactions.

#### Category prefixes

| Prefix | Meaning | Examples |
|--------|---------|----------|
| `dim_` | Dimension table | `dim_customers`, `dim_products` |
| `fact_` | Fact table | `fact_sales` |
| `report_` | Report table | `report_customers`, `report_sales_monthly` |

## 🧱 Naming Columns

### Surrogate Keys

The primary key of every dimension table is a surrogate key and ends with `_key`.

```text
<table_name>_key
```

| Part | Description |
|------|-------------|
| `<table_name>` | The entity the key identifies. |
| `_key` | Suffix that marks the column as a surrogate key. |

**Example:** `customer_key` is the surrogate key of `dim_customers`.

### Technical Columns

Columns generated by the system (metadata, not business data) always start with `dwh_`, followed by a name that explains their purpose.

```text
dwh_<column_name>
```

| Part | Description |
|------|-------------|
| `dwh_` | Prefix reserved exclusively for system-generated metadata. |
| `<column_name>` | What the column is used for. |

**Example:** `dwh_create_date` stores the date the record was loaded into the warehouse.

## ⚙️ Naming Stored Procedures

Every procedure that loads data is named after the layer it feeds.

```text
load_<layer>
```

| Part | Description |
|------|-------------|
| `<layer>` | The layer being loaded: `bronze`, `silver` or `gold`. |

**Examples:**

- `load_bronze`: loads data into the Bronze layer.
- `load_silver`: loads data into the Silver layer.
